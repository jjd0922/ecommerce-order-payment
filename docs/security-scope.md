# 보안 범위와 결제 신뢰 경계

## 범위

현재 구현 범위에는 인증과 인가를 포함하지 않는다. 이 프로젝트는 주문, 결제, 재고 예약, 멱등성, Outbox, 복구 흐름에 집중한다.

운영 환경으로 확장하기 전에는 Spring Security 기반 JWT 또는 세션 인증을 추가해야 한다. 인가 규칙은 최소한 호출자가 자기 계정 또는 테넌트의 주문과 결제만 조회하거나 변경할 수 있도록 제한해야 한다.

## 결제 신뢰 경계

클라이언트가 보낸 결제 데이터는 신뢰 경계 밖의 입력이다.

- `orderId`는 결제할 주문을 식별하는 값일 뿐이다. 서버는 저장된 주문과 주문 라인을 조회해 결제 금액을 다시 계산해야 한다.
- 결제 금액, 통화, 상품 가격, 할인 금액은 요청 본문 값을 그대로 신뢰하지 않는다.
- 실제 PG 연동에서는 결제 결과를 반영하기 전에 PG 서명 또는 webhook 인증 헤더를 검증해야 한다.
- 클라이언트 redirect 확인 흐름과 PG webhook 확인 흐름은 같은 서버 측 상태 전이 서비스를 사용해야 한다.

## 멱등키 정책

`Idempotency-Key`는 클라이언트 재시도 키이며 인증 수단이 아니다.

권장 검증 정책은 다음과 같다.

- 빈 값은 거절한다.
- 길이는 36자에서 128자 사이처럼 작은 범위로 제한한다.
- UUID v4 또는 문서화된 고엔트로피 토큰 형식을 권장한다.
- 제어 문자와 공백 문자는 거절한다.
- 멱등성 레코드에 저장하는 요청과 응답 payload는 크기를 제한한다.

멱등성 레코드 TTL은 외부 재시도 계약에 맞춘다. 일반적으로 24시간에서 7일 범위를 사용한다.

## Rate Limiting

결제 준비와 결제 승인 엔드포인트는 운영 전 rate limit을 적용해야 한다.

권장 정책은 다음과 같다.

- 인증된 일반 트래픽은 계정 또는 사용자 단위로 제한한다.
- 인증 전 또는 공개 엔드포인트는 IP 단위로 더 엄격하게 제한한다.
- Bucket4j 또는 API Gateway 정책을 사용할 수 있다.
- 제한을 초과하면 `429 Too Many Requests`와 재시도 힌트를 반환한다.

## 로그

보안에 민감한 값은 로그에 남기지 않는다.

- PG credential, signature, access token, authorization header 원문은 로그에 남기지 않는다.
- 결제 엔드포인트의 요청 본문 전체를 로그에 남기지 않는다.
- 추적을 위해 `requestId`, `traceId`, `spanId`, `orderId`, `paymentId` 같은 구조화 MDC 키만 사용한다.
